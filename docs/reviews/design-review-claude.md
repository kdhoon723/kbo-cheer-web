## 1. 높음

### R-01 같은 영상 안에서 곡을 바꾸면 끝 시각 감시가 멈추거나, 새 곡이 바로 끊길 수 있다

- 위치: 8.3, 7.4(PlaybackStatus)
- 문제: 끝 시각 감시 타이머는 status가 `playing`·`fading`일 때만 돈다. `play()`는 status를 `starting`으로 바꾸고, `onStateChange(PLAYING)`이 와야 다시 `playing`이 된다. 그런데 같은 모음 영상 안에서는 `seekTo + playVideo`로 곡을 바꾼다.
- 일어나는 장면:
  1. 노시환 곡이 재생 중이다(PLAYING). 이어서 강백호 버튼을 누른다. 같은 영상이라 `seekTo`만 한다. 이동할 구간이 이미 버퍼에 있으면 플레이어 상태가 PLAYING 그대로라 `onStateChange`가 오지 않을 수 있다. 그러면 status가 `starting`에 머물고 감시 타이머가 돌지 않는다. 강백호 곡이 끝 시각을 지나 다음 선수 곡까지 이어진다(NFR-04, BR-02 위반).
  2. 반대로 감시 타이머가 도는 중에 `seekTo` 직후 `getCurrentTime()`이 아직 이전 위치를 돌려주면, 새 곡이 시작하자마자 끝 시각을 넘은 것으로 판단해 멈출 수 있다. 예: 30:00 곡에서 5:00~6:00 곡으로 바꾸는데 첫 확인에서 30:00이 읽히는 경우.
- 개선안:
  - 감시 타이머를 status가 아니라 "nowPlaying이 있는 동안"으로 건다.
  - 재생 여부는 이벤트 대신 매 확인 때 `player.getPlayerState()`로 읽는다.
  - `play()` 때 `seekIssuedAt`을 ref에 적는다. 1.5초 안에는 `t < song.start - 1` 또는 `t > song.end + 1`인 값(이동 전 위치)을 무시하고, 그 뒤에는 그대로 판단한다.
  - STEP 3에서 "같은 영상 안 곡 연속 전환 10회"를 확인 항목으로 둔다.
- 심각도: 높음

### R-02 휴대폰에서 버튼으로 첫 재생이 막힐 수 있는데, 안내와 감지 방식이 맞지 않다

- 위치: 8.6(자동 재생 제한), EX-12, 13절 D-05
- 문제:
  - 설계는 "버튼 클릭 처리 함수 안에서 `playVideo`를 부르면 소리가 난다"고 가정한다. 하지만 플레이어는 다른 출처(youtube.com)의 iframe이고, 명령은 postMessage로 전달된다. 브라우저가 부모 페이지의 사용자 동작을 iframe 재생 허가로 넘겨주는지는 브라우저마다 다르다. 공식 문서는 "대부분의 브라우저가 데스크톱, 모바일, 기타 환경에서 자동 재생을 막을 수 있다"고만 쓴다.
  - 설계는 막혔는지를 2.5초 타이머로 짐작한다. 그런데 공식 API에 `onAutoplayBlocked` 이벤트가 있고, `@types/youtube`의 `Events`에도 선언되어 있다.
  - 막혔을 때 앱 버튼을 "한 번 더 눌러" 봐야 같은 이유로 다시 막힐 수 있다.
- 일어나는 장면: 휴대폰(특히 iOS Safari)에서 앱을 열고 첫 선수 버튼을 눌렀는데 소리가 나지 않는다. "한 번 더 눌러 주세요"를 보고 다시 눌러도 그대로다. 사용자는 앱이 고장 났다고 생각한다. (확인 필요: 실기기에서 아직 확인하지 않았다)
- 개선안:
  - 막힘 감지는 `onAutoplayBlocked` 이벤트로 바꾼다. 2.5초 타이머는 그 이벤트를 받지 못하는 경우의 보조로만 남긴다.
  - 막히면 "영상을 한 번 직접 눌러 재생을 허용해 주세요"라고 안내한다. 사용자가 플레이어를 한 번 누르면 그 뒤로는 버튼으로 재생된다. 이렇게 하려면 플레이어가 화면에 보여야 하므로 D-05 (a)를 뒷받침하는 근거가 된다.
  - STEP 3 첫 구현 단위로 "휴대폰 실기기(Android Chrome, 가능하면 iOS Safari)에서 버튼으로 첫 재생"을 먼저 확인한다. 이 확인이 실패하면 화면 설계가 바뀌기 때문이다.
- 심각도: 높음

## 2. 중간

### R-03 정상 줄 하나가 크게 틀리면 뒤의 정상 줄들이 모두 "시각 이상"으로 잡힌다

- 위치: 4.3
- 문제: anchor를 "바로 앞의 anchor보다 크면 정상"으로 앞에서부터 한 번에 정한다. 그래서 너무 큰 쪽으로 틀린 줄이 있으면, 그 줄이 anchor가 되고 뒤의 바른 줄들이 이상으로 잡힌다.
- 일어나는 장면:
  - 두산 설명란에서 `39:15`를 `49:15`로 잘못 적었다고 하자(영상 길이 56분 안).
  - `49:15`가 anchor가 되고, 뒤의 `42:05`, `43:31`, `45:39`처럼 바른 줄이 줄줄이 경고로 바뀐다.
  - 정작 틀린 `49:15`는 정상으로 남는다. 사용자는 바른 줄을 여러 개 고쳐야 하고, 틀린 줄은 찾지 못한다.
  - 지금 데이터의 오타(`30:36`)는 작은 쪽으로 틀려서 이 문제가 드러나지 않았을 뿐이다.
- 개선안:
  - anchor를 "설명란 순서를 지키면서 시각이 증가하는 가장 긴 부분열(LIS)"로 고른다. 경고 줄 수가 가장 적어진다.
  - 줄이 60개 안팎이라 O(n²) 동적 계획법으로 충분하다. 현재 두산 데이터에서는 지금 알고리즘과 같은 결과(30:36 한 줄만 경고)가 나온다.
  - 같은 길이의 LIS가 여럿이면 앞쪽 줄을 우선한다.
- 심각도: 중간

### R-04 타이머 콜백이 오래된 상태 값을 읽는다

- 위치: 8.3, 8.5
- 문제: 감시 타이머와 페이드 타이머는 setInterval 콜백 안에서 `status`, `settings.volume`, `canControlVolume`을 읽는다. 이 콜백은 만들어진 렌더링의 값을 붙잡고 있다.
- 일어나는 장면:
  - 페이드 도중 볼륨을 70 → 30으로 내린다. 그러면 `finish()`가 옛 값 70으로 볼륨을 되돌려, 다음 곡이 크게 나온다.
  - `startFade` 직후 `setStatus('fading')`가 반영되기 전에 다음 확인이 돌면, 페이드가 두 번 시작될 수 있다.
- 개선안: 타이머에서 읽는 값은 모두 ref(`statusRef`, `volumeRef`, `fadingRef`)에 두고, 렌더링용 state와 함께 갱신한다. "타이머·이벤트 처리기는 ref만 읽는다"를 설계 원칙(0.1)에 적는다.
- 심각도: 중간

### R-05 개발 모드(StrictMode)에서 플레이어가 두 개 만들어질 수 있다

- 위치: 8.2, 8.7
- 문제: 스크립트 로드는 비동기다. StrictMode에서 effect가 "마운트 → 정리 → 다시 마운트"로 두 번 돌면, 두 번 모두 같은 Promise를 기다리게 된다.
- 일어나는 장면:
  - 첫 번째 effect는 정리 함수에서 `playerRef`가 아직 null이라 지울 것이 없다.
  - Promise가 풀리면 두 콜백이 모두 `createPlayer()`를 부른다. `!playerRef.current` 검사는 두 번째 호출을 막는다.
  - 하지만 `attachHost`에서도 생성을 시도하므로, 생성 경로가 둘이라 순서에 따라 iframe이 두 개 붙을 수 있다. 그러면 개발 중 소리가 두 겹으로 나거나 이벤트가 엇갈린다.
- 개선안:
  - effect 안에 `let cancelled = false`를 두고 `.then(() => { if (!cancelled) createPlayer() })`, 정리 함수에서 `cancelled = true`로 한다.
  - 생성 경로를 하나로 줄인다. `attachHost`는 host만 기록하고, 생성은 "api ready && host 있음"을 보는 effect 하나에서 한다.
- 심각도: 중간

### R-06 노트북에서 곡 버튼을 누른 뒤 Space로 정지하면 같은 곡이 다시 시작될 수 있다

- 위치: 12.5, BR-36
- 문제: 선수 버튼을 마우스로 누르면 그 버튼에 포커스가 남는다. 포커스된 버튼에서 Space를 누르면 브라우저는 keyup 때 그 버튼을 클릭한다. 설계는 입력칸에서만 단축키를 끄고, 버튼에 포커스가 있을 때는 따로 처리하지 않는다.
- 일어나는 장면:
  1. 노시환을 클릭한 뒤 Space를 누른다.
  2. keydown에서 `stop()`이 불린다.
  3. keyup에서 포커스된 노시환 버튼이 눌려 곡이 다시 시작된다.
  - Enter도 같은 문제가 있다(Enter는 단축키가 아니라 버튼 기본 동작).
  - (확인 필요: keydown에서 `preventDefault`를 하면 keyup 클릭이 막히는지는 브라우저별로 STEP 3에서 확인한다)
- 개선안:
  - Space 처리 때 keydown과 keyup을 모두 `preventDefault`한다.
  - 재생 버튼은 클릭 뒤 포커스를 남기지 않게 한다(`onMouseDown`에서 `preventDefault`, 또는 클릭 처리 후 `blur()`). 키보드로 버튼을 고르는 사용자의 포커스 표시는 유지되도록, 마우스·터치 클릭일 때만 적용한다.
- 심각도: 중간

### R-07 휴대폰 세로 화면에서 선수 격자가 보이는 공간이 너무 좁다

- 위치: 5.2, 13절 D-05
- 문제: 휴대폰 배치는 위·아래가 고정 영역으로 차 있다.
  - 위: 머리말(약 56px)과 플레이어(200px)
  - 아래 고정: 상황 버튼 줄(롯데는 상황 곡 8개라 2줄, 약 100px)과 조작줄(응원가로, 지금→응원가 시작, 정지, 볼륨이 2줄, 약 100px)
- 일어나는 장면: 360×640 화면에서 격자가 보이는 높이는 약 180px, 선수 버튼 3줄(9명)쯤이다. 타자가 나올 때마다 격자를 스크롤해야 해서 "버튼 한 번"이라는 목적이 약해진다.
- 개선안:
  - 조작줄을 한 줄로 줄인다(재생 중 곡 이름, 응원가로, 정지). 「지금 → 응원가 시작」과 볼륨은 재생 중 곡 이름을 누르면 펼쳐지는 줄로 옮긴다.
  - 상황 버튼 줄은 한 줄로 두고, 그 줄 안에서만 가로로 넘긴다(페이지 가로 스크롤 금지 NFR-01과 충돌하지 않음).
  - 플레이어는 D-05 (a) 조건(200×200)을 지키되, 휴대폰에서는 200×200 정사각형을 조작줄 옆에 둘지 STEP 3 화면 캡처로 비교해 정한다.
  - 수용 기준에 "360×640에서 격자 4줄 이상 보임" 같은 숫자를 넣을지 정한다.
- 심각도: 중간

### R-08 접속 주소가 바뀌면 그 기기의 곡 목록이 사라진 것처럼 보인다

- 위치: 3.1, 1.3(실행 방식), NFR-12
- 문제: LocalStorage는 출처(프로토콜 + 호스트 + 포트)마다 따로다. 설계는 이 점을 다루지 않는다.
- 일어나는 장면:
  - 휴대폰이 어제 `http://192.168.0.10:5173`으로 접속해 응원가 시작 지점을 20명 지정했다.
  - 오늘 노트북 IP가 DHCP로 `192.168.0.23`이 됐다. 휴대폰 주소가 바뀌어 빈 저장소에서 처음 데이터로 시작하고, 어제 지정한 값이 안 보인다(지워지지는 않았지만 예전 주소로만 보인다).
  - 노트북에서도 `localhost:5173`과 `127.0.0.1:5173`은 서로 다른 저장소다.
- 개선안:
  - 실행 안내(README 또는 화면 안내)에 "노트북은 항상 `localhost:5173`으로 연다", "휴대폰 주소가 바뀌면 JSON 가져오기로 옮긴다"를 적는다.
  - 공유기에서 노트북 IP를 고정(DHCP 예약)하라고 권한다.
  - 설정 화면에 "이 브라우저 저장소: <현재 출처>"를 한 줄 보여 주면 원인을 바로 알 수 있다. 요구사항에 없는 표시라 채택 여부를 정해야 한다.
- 심각도: 중간

### R-09 처음 데이터 절차에 "직접 듣고 정하기"가 있는데 누가 하는지 정해지지 않았다

- 위치: 11절 4단계, D-04
- 문제: 두 단계가 소리를 들어야 할 수 있다.
  - 두산 `서울 두산 승리하리라`의 실제 시각 찾기
  - 구단 고유 곡(체로키, 셀리오, 환희, 시그널, 리듬 응원 송, Let's GO, 기아 없이는 못살아, 승리하리라 KT WIZ 등) 분류
  - 구현과 화면 확인은 자동으로 할 수 있지만, 음악을 듣고 판단하는 일은 사람이 해야 한다.
- 개선안:
  - 두산 시각은 근거로 먼저 정할 수 있다. `30:36`은 39:15와 42:05 사이에 있어야 하는데, 숫자 한 자리만 바꾼 `40:36`이 그 사이에 들어간다. 앞 곡 `챔피언 두산`이 1분 21초(39:15~40:36)이고 뒤 곡이 1분 29초(40:36~42:05)라 다른 곡 길이(1~2분)와도 맞다. 그래서 `40:36`을 기본값으로 하고, 학생(김도훈)이 한 번 들어 확인한다.
  - 고유 곡은 설명란 위치로 기본 분류한다. 첫 구분선 앞이나 선수 구획 사이에 있으면 상황 곡, 마지막 구분선 뒤면 팀 응원가다. 학생이 목록만 보고 바꿀 곡을 알려 주는 방식으로 한다.
  - 11절에 "듣기가 필요한 항목은 학생 확인"이라고 적는다.
- 심각도: 중간

### R-10 노트북에서 게임을 전체 화면으로 하면 끝 시각 정지가 늦어질 수 있다

- 위치: 8.3, NFR-04
- 문제: 같은 노트북에서 게임을 전체 화면으로 하면 브라우저 창이 가려진다. 브라우저는 가려지거나 숨겨진 탭의 타이머를 늦춘다(보통 1초에 한 번, 오래 숨겨지면 더 느리게).
- 일어나는 장면: 감시 간격이 200ms에서 1초 이상으로 늘어나, 끝 시각을 넘어 다음 선수 곡 앞부분이 들린다. 끝 1초 전에 시작하는 페이드도 건너뛰거나 뚝 끊길 수 있다. (확인 필요: 소리가 나는 탭이 이 제한에서 빠지는지는 브라우저와 OS마다 달라 STEP 3에서 확인한다)
- 개선안:
  - 곡을 시작할 때 `loadVideoById({ videoId, startSeconds, endSeconds })`로 플레이어 자체 끝 시각도 함께 건다. 탭이 숨겨져도 플레이어가 멈춘다.
  - 공식 문서는 cue 함수 설명에서 "endSeconds를 준 뒤 seekTo를 부르면 endSeconds가 더는 적용되지 않는다"고 쓴다. 그래서 응원가로(seekTo) 뒤에는 앱 타이머가 계속 필요하다. 두 방식을 함께 쓴다.
  - 단, 같은 영상에서도 매번 `loadVideoById`를 하면 곡 전환이 느려질 수 있다. STEP 3에서 seekTo와 loadVideoById의 전환 시간을 재서 고른다.
  - 8.3의 근거 문장("이전 endSeconds가 남을 수 있다")은 문서 내용과 다르므로 고친다. 문서상으로는 seekTo 뒤 endSeconds가 풀린다.
- 심각도: 중간

### R-11 브라우저나 OS가 재생을 멈추면 화면이 계속 "재생 중"으로 남는다

- 위치: 8.3(onStateChange), 7.4(PlaybackStatus)
- 문제: onStateChange는 PLAYING과 ENDED만 처리한다. 앱 밖의 이유로 PAUSED가 될 때는 처리가 없다. 예: 휴대폰 전화 수신, 다른 앱의 소리, 이어폰 분리, 잠금 화면 제어.
- 일어나는 장면: 전화를 받고 돌아오면 소리는 멈췄는데, 조작줄에는 "▶ 노시환"과 활성화된 「응원가로」가 그대로 있다. 감시 타이머도 계속 돈다.
- 개선안: 앱이 멈춘 것이 아닌 PAUSED(앱의 `finish()`가 부른 pause가 아님)를 받으면 재생 상태를 idle로 바꾸고 nowPlaying을 비운다. 앱이 부른 pause인지 구분하려고 `pausingByAppRef`를 둔다.
- 심각도: 중간

### R-12 오류 코드 153과 `window.YT` 타입 선언이 빠졌다

- 위치: 8.6, 8.1, 2절
- 문제:
  - 공식 문서의 onError 목록에 153("요청에 HTTP Referer 헤더나 API 클라이언트 식별 정보가 없음")이 있는데 설계 표에 없다. `@types/youtube`의 `PlayerError` 열거형에도 153이 없어, 값을 비교하려면 숫자로 다뤄야 한다.
  - `@types/youtube`는 `declare namespace YT`만 선언한다. `window.YT`와 `window.onYouTubeIframeAPIReady`는 선언하지 않는다(index.d.ts에 `interface Window` 확장 없음). 그래서 8.1 의사코드를 그대로 쓰면 TypeScript 오류가 나고, 이를 피하려고 `any`나 검사 없는 `as`를 쓰게 될 위험이 있다(NFR-09).
- 개선안:
  - `src/youtube-global.d.ts`에 `interface Window { YT?: typeof YT; onYouTubeIframeAPIReady?: () => void }`를 선언한다.
  - onError 처리는 `const code: number = e.data`로 숫자로 받아 2·5·100·101·150·153을 분기한다. 153은 "재생 정보를 확인하지 못했습니다(페이지 설정 문제)"로 안내한다.
  - 페이지의 `Referrer-Policy`를 `no-referrer`로 바꾸지 않는다는 점을 0.1에 적는다.
- 심각도: 중간

## 4. 문제없다고 판단한 항목

- 기능 요구사항 반영: FR-01~28이 모두 14.1 추적표에 컴포넌트·함수·절로 연결되어 있고, 빠진 FR은 없다.
- 수정·삭제 대상 구분: 모든 수정·삭제가 곡 ID 하나로 이뤄진다. 영상 ID는 수정할 수 없고(BR-22), 삭제는 한 곡만 지운다(BR-23). JSON 가져오기·되돌리기만 전체를 바꾸고 확인을 거친다.
- 시각 역행 처리(현재 데이터 기준): 프로토타입 결과 두산 1줄만 경고되고, 앞 곡 `챔피언 두산`의 끝이 42:05로 줄지 않는다. 고친 시각을 "앞뒤 anchor 사이"로만 받아 다른 줄이 바뀌지 않는다.
- 중복 상황 곡과 끝 시각: 중복 챕터를 후보에서는 빼고 경계에는 남기는 구조가 맞다. 키움 `권혁빈` 10:46 → 11:14로 확인했다. 선수 수 합계 235로 조사 결과와 같다.
- LocalStorage 일관성의 기본 구조: 지연 초기화로 한 번 읽고, 상태가 바뀔 때 useEffect로 쓰는 단방향 구조라 컴포넌트가 저장소를 직접 건드리지 않는다. 키를 셋으로 나눠 피해 범위를 줄였다.
- 형식 검사: 외부 입력을 unknown으로 받아 타입 가드를 거치는 원칙, version 검사, JSON 파일과 처음 데이터를 같은 형식·같은 검사 함수로 다루는 구조
- Data API 오류 분류: 실제 응답 3종(ACCESS_DENIED, API_KEY_HTTP_REFERRER_BLOCKED, API_KEY_INVALID)과 빈 items를 근거로 했다. LAN 접속에서는 호출 자체를 하지 않는다.
- 플레이어를 AppLayout에 하나만 두는 구조: 팀 전환 중 재생 유지(BR-06)를 별도 코드 없이 만족한다. React가 그리지 않는 안쪽 div에 iframe을 붙이는 방식도 맞다.
- 단축키 `e.code` 판단, 입력칸에서 끄기, 메인 화면에서만 켜기
- 곡 ID를 보안 컨텍스트 없이 만드는 방식(http LAN 접속 대응)
- Context 나누기: 곡 목록(useReducer), 팀·설정, 재생, 알림. 의존 순서대로 Provider를 쌓아 순환 의존이 없다.
