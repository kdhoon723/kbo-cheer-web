# 설계 검토 결과 (Codex CLI)

- 검토 도구: Codex CLI 0.167.0, 모델 gpt-6.1-sol, 읽기 전용 실행(파일 수정 불가)
- 프롬프트: Claude Code 검토(design-review-claude.md)와 같은 설계 검토 프롬프트
- 아래는 Codex 답변 원문이다. 비교하기 쉽게 항목 번호 앞에 C-를 붙이고, 로컬 파일 경로 링크만 상대 이름으로 바꿨다.

---

검토 결과는 **보완 필요**입니다. [요구사항](requirements.md)의 FR-01~28은 모두 [설계](design.md)에 연결되어 있습니다. 다만 일부 기능은 요구사항과 충돌하거나, 안전하게 동작하기 위한 상태 전이가 빠져 있습니다.

아래 위치는 **설계서의 절 번호**입니다. 문서상 결함과 구현 시 보완해야 할 공백을 구분했습니다. 파일 생성·수정이나 코드 작성은 하지 않았습니다.

C-01. **플레이어 객체의 존재를 준비 완료로 판단한다**
   
   - **위치:** 8.2, 8.3절
   - **문제:** `play()`는 `playerRef`가 있는지만 확인합니다. `new YT.Player()`로 객체가 생긴 시점과 `onReady`가 발생한 시점은 다릅니다.
   - **왜 문제인가:** iframe이 준비 중일 때 곡을 누르면 `setVolume`, `seekTo`, `loadVideoById`를 너무 일찍 호출할 수 있습니다. 공식적인 API 호출 준비 기준은 `onReady`입니다. [YouTube 공식 문서](https://developers.google.com/youtube/iframe_api_reference#Events)
   - **개선안:** 스크립트 로드 상태와 플레이어 준비 상태를 구분하고, `onReady` 전에는 최신 재생 요청 하나만 보관합니다.
   - **심각도:** **높음**

C-02. **준비 전 재생 요청의 취소 규칙이 없다**
   
   - **위치:** 8.3, 8.5, 8.7절
   - **문제:** 준비 전 요청은 `pendingRef`에 남기지만, 정지·삭제·cleanup에서 이를 취소하는 처리가 명시되지 않았습니다.
   - **왜 문제인가:** 로딩 중 곡 선택 → 정지 또는 곡 삭제 → `onReady` 도착 순서에서 취소한 곡이 재생될 수 있습니다. 비동기 로드 완료 후 정리된 컴포넌트가 다시 플레이어를 생성하는 경우도 막아야 합니다.
   - **개선안:** 정지·삭제·cleanup에서 대기 요청과 관련 타이머를 취소합니다. 비동기 완료 시에는 해당 작업이 여전히 유효한지 확인하고, 플레이어가 없어도 정지는 안전하게 처리되도록 합니다. [React 비동기 cleanup 원칙](https://react.dev/reference/react/useEffect#fetching-data-with-effects)
   - **심각도:** **높음**

C-03. **200ms 폴링으로 정지 오차의 상한을 보장한다**
   
   - **위치:** 8.3절
   - **문제:** “끝 시각을 넘는 시간은 최대 약 0.2초”라는 설명은 성립하지 않습니다.
   - **왜 문제인가:** 메인 스레드가 지연되면 타이머도 늦게 실행되어 다음 챕터가 들릴 수 있습니다. `setInterval`의 간격은 최대 지연 시간이 아닙니다. NFR-04 충족 근거가 부족합니다. [MDN 타이머 설명](https://developer.mozilla.org/en-US/docs/Web/API/Window/setInterval#delay_restrictions)
   - **개선안:** 플레이어의 종료 구간 지정과 보조 폴링을 함께 사용하는 방안을 검토하고, 같은 영상 이동까지 포함해 검증해야 합니다. “`seekTo` 뒤 이전 `endSeconds`가 남는다”는 설계 근거도 공식 문서만으로 확정하기 어려우므로 확인이 필요합니다. [YouTube 구간 지정 문서](https://developers.google.com/youtube/iframe_api_reference#Queueing_Functions)
   - **심각도:** **높음**

C-04. **정지를 연속으로 누르면 페이드 타이머가 중복될 수 있다**
   
   - **위치:** 8.5절
   - **문제:** `startFade()`에 기존 페이드 취소나 중복 실행 방어가 없습니다.
   - **왜 문제인가:** 정지를 두 번 누르면 타이머 참조가 덮어써질 수 있습니다. 이후 새 곡을 재생해도 참조를 잃은 이전 타이머가 남아 새 곡의 볼륨을 줄이거나 `finish()`를 호출할 위험이 있습니다.
   - **개선안:** 이미 페이드 중이면 추가 정지를 무시하거나, 기존 타이머를 취소한 후 새 타이머를 만듭니다.
   - **심각도:** **높음**

C-05. **API 실패 분기에서 정상 처리로 계속 진행한다**
   
   - **위치:** 10.4절
   - **문제:** `!r.ok`와 퍼가기 불가 분기에서 오류 상태만 설정하고 종료하지 않습니다.
   - **왜 문제인가:** 할당량 초과 응답에는 `r.data`가 없는데 다음 줄에서 접근합니다. 명시한 `ApiResult` 판별 유니온에도 맞지 않아 그대로 구현하면 타입 오류가 발생합니다. 퍼가기 불가 영상도 후보 생성으로 진행합니다.
   - **개선안:** 실패 분기에서 즉시 반환하거나, 정상 처리와 상호 배타적인 분기로 구성합니다.
   - **심각도:** **중간**

C-06. **정상 후보의 시작 시각 편집을 금지해 FR-12를 축소한다**
   
   - **위치:** 2, 4.6절
   - **문제:** 확인 단계에서 시작 시각을 고칠 수 있는 후보를 `anchor`가 아닌 후보로 제한했습니다.
   - **왜 문제인가:** 순서는 정상인데 실제 음악보다 2초 빠른 챕터를 확인해도, 먼저 저장한 뒤 수정 화면으로 이동해야 합니다. FR-12에는 이런 제한이 없습니다.
   - **개선안:** 정상 후보도 편집하게 하고, 변경된 시각의 순서·범위를 검사해 관련 끝 시각을 다시 계산합니다.
   - **심각도:** **중간**

C-07. **연속된 시각 이상 후보를 교정할 때 서로의 순서를 검사하지 않는다**
   
   - **위치:** 4.6절
   - **문제:** 교정 값이 앞뒤 `anchor` 사이에 있는지만 확인합니다.
   - **왜 문제인가:** 정상 경계가 10:00과 20:00이고 이상 후보가 두 개일 때, 두 후보를 각각 15:00과 14:00으로 고쳐도 모두 통과합니다. 같은 시각으로 고치는 경우도 막지 못합니다.
   - **개선안:** 교정된 후보를 포함해 설명란 순서대로 시작 시각이 엄격하게 증가하는지 검사합니다. 시각 중복도 경고 대상으로 둡니다.
   - **심각도:** **중간**

C-08. **상황 곡 중복 방지가 최초 파싱에만 적용된다**
   
   - **위치:** 4.5, 4.6, 7.2, 12.2절
   - **문제:** 후보의 종류·이름을 바꾼 뒤 중복을 다시 검사하지 않습니다. 단일 등록·곡 수정·JSON 가져오기에도 중복 처리 계약이 없습니다.
   - **왜 문제인가:** 서로 다른 후보를 모두 「볼넷 송」으로 바꾸거나, 기존 상황 곡과 같은 제목으로 단일 등록하면 같은 버튼이 두 개 생길 수 있습니다. FR-07 수용 기준과 맞지 않습니다.
   - **개선안:** 현재 후보 값과 저장 목록을 기준으로 중복을 재평가합니다. 저장 단계 또는 표시 단계에서도 같은 제목의 상황 버튼이 중복되지 않도록 규칙을 통일합니다.
   - **심각도:** **중간**

C-09. **시각을 고친 뒤 ‘이미 있음’ 판정이 갱신되지 않는다**
   
   - **위치:** 2, 4.5, 4.6절
   - **문제:** `existing`은 원래 시작 시각으로 한 번 계산하고 후보 상태에 저장합니다.
   - **왜 문제인가:** 두산 곡을 40:36으로 고쳐 저장한 뒤 다시 가져오면, 원문의 30:36으로 비교하므로 기존 곡을 찾지 못합니다. 다시 40:36으로 고쳐도 표시가 갱신되지 않습니다.
   - **개선안:** `existing`을 현재 시작 시각·영상 ID·최신 팀 곡 목록에서 계산하는 파생 값으로 둡니다. 교정 후 기본 선택 처리도 정의해야 합니다.
   - **심각도:** **중간**

C-10. **응원가 시작 지정 버튼의 활성 상태를 갱신할 경로가 없다**
    
    - **위치:** 7.4, 8.3절
    - **문제:** Context에는 현재 시각 상태가 없고, 감시 타이머도 시간 변화에 따른 React 상태 갱신을 하지 않습니다.
    - **왜 문제인가:** 시작 시각에서 비활성으로 그려진 버튼이 재생 위치가 유효 구간에 들어간 뒤에도 계속 비활성일 수 있습니다. FR-19·EX-23의 동작을 보장하지 못합니다.
    - **개선안:** 현재 시각 또는 버튼 활성 여부를 주기적으로 갱신하는 계약을 추가합니다. 전체 화면을 매번 다시 그리지 않도록 필요한 값만 갱신하면 됩니다.
    - **심각도:** **중간**

C-11. **외부 이벤트 콜백이 최신 상태를 읽는 방법이 불명확하다**
    
    - **위치:** 8.2, 8.3, 8.5, 8.7절
    - **문제:** 처음 등록한 플레이어 콜백과 타이머가 최신 `status`, `settings.volume`을 읽는 방식이 없습니다. `nowPlayingRef`만으로는 다른 상태까지 해결되지 않습니다.
    - **왜 문제인가:** 이전 볼륨을 기준으로 페이드를 시작해 소리가 갑자기 커지거나, 페이드 중 발생한 이벤트가 과거 상태를 보고 `playing`으로 되돌릴 수 있습니다. 일반 콜백은 등록 당시 상태를 계속 참조할 수 있습니다. [React 상태 캡처 설명](https://react.dev/learn/separating-events-from-effects#declaring-an-effect-event)
    - **개선안:** 외부 콜백이 필요한 최신 값을 ref로 읽도록 하거나, 적절한 의존성과 cleanup으로 콜백을 갱신합니다.
    - **심각도:** **중간**

C-12. **스크립트 타임아웃과 재시도의 정리가 불완전하다**
    
    - **위치:** 8.1절
    - **문제:** 타임아웃에서는 스크립트를 제거하지 않고, 성공 시 타임아웃 해제와 전역 ready 콜백 정리도 없습니다.
    - **왜 문제인가:** 느린 네트워크에서 재시도하면 이전 스크립트와 콜백 체인이 남습니다. 이전 요청의 늦은 오류가 새 요청의 `apiPromise`를 비울 가능성도 있습니다.
    - **개선안:** 성공·실패 공통 종료 처리에서 타이머와 해당 요청의 자원을 정리하고, 이전 요청이 새 요청의 상태를 변경하지 못하게 합니다.
    - **심각도:** **중간**

C-13. **장기 버퍼링과 일부 플레이어 오류의 처리 경로가 없다**
    
    - **위치:** 8.3, 8.6절
    - **문제:** 2.5초 확인에서 `BUFFERING`을 제외하지만, “버퍼링이 이어짐”을 판정할 별도 시간 기준은 없습니다. `PAUSED` 처리와 미등록 오류 코드의 기본 처리도 불명확합니다.
    - **왜 문제인가:** 네트워크가 끊겨 버퍼링에 머물러도 아무 안내가 없거나, 실제 플레이어와 화면의 재생 상태가 달라질 수 있습니다.
    - **개선안:** 버퍼링 대기 제한과 일시정지 상태 처리를 정의합니다. `onAutoplayBlocked`를 활용하고, 오류 153 및 알 수 없는 오류도 안전하게 종료·안내하도록 합니다. [YouTube 이벤트 문서](https://developers.google.com/youtube/iframe_api_reference#Events)
    - **심각도:** **중간**

C-14. **수정 주소의 팀 불일치와 없는 곡 처리가 빠져 있다**
    
    - **위치:** 5.1, 6.2, 12.2절
    - **문제:** 수정 대상은 전역 목록에서 `songId`로 찾으며, URL의 `teamId`와 일치하는지 검사하는 규칙이 없습니다.
    - **왜 문제인가:** 한화 경로에 삼성 곡 ID를 넣으면 한화 화면에서 삼성 곡을 수정할 수 있습니다. 삭제되거나 JSON 교체로 사라진 곡의 주소를 다시 열었을 때의 처리도 없습니다.
    - **개선안:** `songId`와 `teamId`가 모두 일치하는 곡만 편집하고, 없으면 안내와 곡 관리 화면 복귀 경로를 제공합니다.
    - **심각도:** **중간**

C-15. **처음 데이터로 되돌리기의 확인 단계가 빠져 있다**
    
    - **위치:** 6.2, 7.2절
    - **문제:** `resetToSeed()`는 정의되어 있지만 확인·취소 흐름은 없습니다.
    - **왜 문제인가:** 그대로 구현하면 클릭 한 번으로 사용자 곡 목록 전체를 바꿀 수 있습니다. FR-22·BR-39는 확인 후 실행을 요구합니다.
    - **개선안:** SettingsPage에서 확인을 받은 경우에만 실행하고, 취소하면 아무 상태도 바뀌지 않도록 명시합니다.
    - **심각도:** **중간**

C-16. **자동 분류 우선순위가 BR-13과 다르다**
    
    - **위치:** 4.4절
    - **문제:** 설계는 선수 접미사 판별을 팀 구획 판별보다 먼저 적용합니다. BR-13의 “마지막 구분선 뒤 = 팀 응원가”와 충돌할 입력이 있습니다.
    - **왜 문제인가:** 마지막 구획에 「○○ 등장곡」이라는 제목이 있으면 설계는 선수 곡으로 분류합니다. 조사한 10개 영상에서는 발생하지 않지만 추가 영상에서는 결과가 달라집니다.
    - **개선안:** 요구사항의 구획 규칙을 우선 적용하고, 예외는 확인 단계의 종류 수정으로 처리합니다.
    - **심각도:** **낮음**

C-17. **시각이 잘못된 첫 중복 곡이 정상 중복 곡을 가릴 수 있다**
    
    - **위치:** 4.3~4.5절
    - **문제:** 중복 집합에 제목을 넣을 때 시각의 유효성을 고려하지 않습니다.
    - **왜 문제인가:** 첫 「공통 안타 송」이 시각 이상이고 뒤의 같은 제목은 정상이라면, 첫 후보만 남고 정상 후보는 제거됩니다. 사용자는 유효한 대체 구간이 있어도 직접 교정해야 합니다.
    - **개선안:** 이상 후보의 경고는 유지하면서 정상 중복 구간을 선택할 수 있게 하거나, 첫 발생과 첫 정상 발생 중 무엇을 대표로 삼는지 명확히 정의합니다. 현재 10개 영상 외 입력에 대한 경계 사례입니다.
    - **심각도:** **중간**

C-18. **여러 탭에서의 LocalStorage 일관성 정책이 없다**
    
    - **위치:** 3.3, 7.2절
    - **문제:** 최초 한 번만 읽으며 다른 탭의 변경을 감지하는 규칙이 없습니다.
    - **왜 문제인가:** 탭 A에서 곡을 삭제한 뒤, 이전 목록을 가진 탭 B에서 다른 곡을 수정하면 삭제했던 곡이 저장소에 다시 나타날 수 있습니다.
    - **개선안:** 단일 탭 사용을 운영 범위로 명시하거나, `storage` 이벤트로 외부 변경을 감지해 갱신·충돌 처리 방식을 정합니다. 여러 탭 지원은 요구사항에 명시되지 않아 보완 제안으로 판단합니다.
    - **심각도:** **낮음**

문제없다고 판단한 항목은 다음과 같습니다.

- **요구사항 추적:** FR-01~28 중 설계 요소가 완전히 빠진 기능은 없습니다.
- **타입 정의:** `TeamId`·`SongKind` 유니온, `ApiResult`·`ImportPhase` 판별 유니온, 외부 입력의 `unknown`·타입 가드 사용은 적절합니다.
- **핵심 파싱:** 두산의 역행 시각을 경계에서 제외하고, 교정 후 앞 곡의 끝을 재계산하는 방식은 타당합니다. 제거한 중복 챕터를 끝 시각 경계로 보존한 것도 적절합니다.
- **수정·삭제 식별:** 고유 ID 기준 처리와 재생 중 곡 사본 보관은 적절합니다. 수정 라우트의 검증만 보완하면 됩니다.
- **저장·구조:** 단일 탭에서 React 상태를 원본으로 두는 방식, 저장 실패 시 화면 유지·안내, 저장 키 분리, 순수 함수·Context·페이지의 책임 분리는 합리적이며 과도한 구조는 보이지 않습니다.
