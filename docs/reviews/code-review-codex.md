- 대상: 커밋 0b37d31(모션까지 반영한 구현 코드)

**검토 결론: 수정 필요 — 높음 1건, 중간 6건입니다.** 독립 구조 검토도 `BLOCK`으로 판단했습니다. 파일은 생성하거나 수정하지 않았습니다.

검증은 정적 검토, 메모리에서 실행한 함수·콜백 재현, lint로 수행했습니다. lint는 오류 0개·경고 5개였습니다. 타입 검사는 비교용 의존성에 `motion/react`가 없어 완료하지 못했고, 브라우저·E2E는 새로 실행하지 않았습니다.

K-01. **[높음] 플레이어 준비가 실패하면 이후 클릭으로 복구할 수 없습니다.**

   **위치:** `src/context/PlayerContext.tsx:284`, 같은 파일 179~186줄.

   **문제:** 스크립트 로드에는 제한시간이 있지만, `YT.Player` 생성 후 `onReady`를 기다리는 경로에는 제한시간·실패 전이가 없습니다.

   **재현:** IFrame API 스크립트는 허용하고 영상 iframe 요청만 차단한 뒤 곡을 누릅니다. `onReady`가 오지 않는 상태에서 다시 곡을 누릅니다.

   **영향:** `apiState='loaded'`, `readyRef=false`가 유지됩니다. 클릭은 대기 곡만 교체하며, 실패 안내와 플레이어 재생성이 없어 재생 기능이 계속 막힙니다. EX-09·10의 예외 처리가 빠진 경로입니다.

   **수정:** 플레이어 준비에도 제한시간을 두고, 실패한 인스턴스를 정리한 뒤 다음 클릭에서 재생성하도록 처리합니다.

K-02. **[중간] 재생 직후 실제 일시정지를 이전 이벤트로 오인합니다.**

   **위치:** `src/context/PlayerContext.tsx:223`, `src/lib/playback.ts:50`.

   **문제:** 새 곡의 `PLAYING`을 이미 받았어도, 이동 후 1.5초 이내의 구간 중간 `PAUSED`를 무조건 잔류 이벤트로 버립니다.

   **재현:** 60~120초 구간 재생 → `PLAYING` 수신 → 800ms에 위치 60.5초의 `PAUSED` 수신. 실제 콜백 모의 실행에서 상태가 `playing`으로 남고 안내가 없음을 확인했습니다. 「응원가로」 직후에도 가능합니다.

   **영향:** 소리는 멈췄지만 화면은 계속 재생 중입니다. 감시 타이머에도 `PAUSED`를 복구하는 분기가 없어 EX-28을 충족하지 못합니다. 이후 자동재생 차단으로 잘못 안내할 수도 있습니다.

   **수정:** 현재 요청의 재생 시작을 확인하면 잔류 이벤트 보호를 해제합니다. 실제 일시정지는 종료·안내로 처리하고, 재생 성공 시 자동재생 검사 타이머도 해제합니다.

K-03. **[중간] 팀·설정 저장 실패를 알리지 않습니다.**

   **위치:** `src/context/PrefsContext.tsx:21`, 25~27줄.

   **문제:** `saveTeamState()`와 `saveSettings()`가 반환하는 실패 여부를 버립니다.

   **재현:** 앱을 연 뒤 저장 용량 부족 등으로 `setItem()`이 실패하게 만들고 팀·볼륨·정렬을 변경한 후 새로고침합니다.

   **영향:** 화면에는 변경이 반영되지만 안내 없이 이전 값으로 돌아갑니다. 곡 목록 저장이 성공한 상태에서 설정 저장만 실패하면 `SongsContext`의 알림도 나오지 않습니다. EX-15 위반입니다.

   **수정:** 반환값을 검사해 저장 실패를 알리고, 저장이 다시 성공할 때까지 같은 알림을 반복하지 않도록 처리합니다.

K-04. **[중간] 정상적으로 가져온 일부 곡 ID에서 수정 화면이 열리지 않습니다.**

   **위치:** `src/pages/SongListPage.tsx:55`.

   **문제:** JSON 검사는 비어 있지 않은 문자열 ID를 허용하지만, 수정 경로에는 ID를 인코딩하지 않고 넣습니다.

   **재현:** 정상 곡의 `id`를 `"a/b"`로 바꾼 JSON을 가져온 뒤 수정을 누릅니다.

   **영향:** `/team/hanwha/songs/a/b/edit`가 수정 라우트와 일치하지 않아 홈으로 이동합니다. JSON 검사 통과와 라우트 불일치를 함수 실행으로 확인했습니다.

   **수정:** 경로를 만들 때 `encodeURIComponent(id)`를 사용합니다.

K-05. **[중간] 기존 상황 곡을 재선택하면 같은 제목으로 중복 저장됩니다.**

   **위치:** `src/lib/candidates.ts:95`.

   **문제:** `existing` 후보를 상황 곡 중복 검사에서 제외합니다. 따라서 기존 곡과 제목까지 같아도 다시 선택할 수 있습니다.

   **재현:** 상황 곡이 등록된 모음 영상을 다시 가져오기 → 해당 「이미 있음」 후보를 체크 → 저장합니다.

   **영향:** 같은 팀에 같은 제목의 상황 곡이 추가됩니다. 실제 평가 결과도 `existing=true`, `duplicate=false`, `willSave=true`였습니다.

   **수정:** 기존 후보에도 제목 중복 제한을 적용합니다. **설계 4.6도 현재 동작을 명시하므로, BR-14의 중복 금지 규칙에 맞춰 설계와 코드를 함께 조정해야 합니다.**

K-06. **[중간] 추가 상황 곡이 다른 상황의 고정 칸을 차지합니다.**

   **위치:** `src/lib/situationSlots.ts:38`.

   **문제:** 같은 범주의 두 번째 곡을 범주와 관계없이 앞쪽 빈 칸에 넣습니다.

   **재현:** 한화의 팀 응원가 하나를 상황 곡으로 바꾸고 제목을 「볼넷 송 2」로 저장합니다. 기존 안타·볼넷 칸이 찬 상태이므로 새 곡은 빈 아웃 칸으로 들어갑니다.

   **영향:** 단축키 `2`가 아웃 대신 볼넷 곡을 재생합니다. FR-07·BR-36의 고정 상황 칸 의미가 깨집니다.

   **수정:** 고정 8칸의 범주를 유지하고, 같은 범주의 추가 곡은 해당 칸의 선택 목록이나 별도 추가 목록으로 제공합니다. **설계 5.2에도 현재 배치 방식이 있어 요구사항과 함께 정리해야 합니다.**

K-07. **[중간] 팀 선택 대화상자에서 Space로 버튼을 누를 수 없습니다.**

   **위치:** `src/hooks/useKeyboardShortcuts.ts:26`.

   **문제:** `keydown`은 대화상자 안에서 단축키를 건너뛰지만, `keyup`은 모든 버튼의 Space 기본 동작을 취소합니다. 버튼의 Space 활성화는 keyup에서 처리됩니다. [Chromium 구현](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/html/html_element.cc#L4152-L4185)

   **재현:** 메인에서 팀 선택 창 열기 → Tab으로 다른 팀이나 닫기 버튼에 이동 → Space.

   **영향:** 기본 클릭이 취소되어 팀 선택·닫기가 실행되지 않습니다. Enter는 동작합니다.

   **수정:** `keyup`에도 대화상자 예외를 적용하거나, 실제 정지 단축키로 소비한 Space만 추적해 취소합니다.
