## 3. 성능 측정

측정 방법:
- 브라우저 콘솔에서 버튼의 `click()`을 부른 순간부터 시간을 잼.
- 20ms마다 `YT.get('yt-player')`로 상태와 위치를 읽음.
- "상태 PLAYING이고, 위치가 새 곡 시작 시각부터 2초 안"이 처음 된 때까지를 응답 시간으로 봄.
- 화면 1280×800, 노트북 브라우저 1개, 측정 직전에 같은 페이지에서 실제 클릭으로 한 곡을 재생해 둠.

## 4. 실패 목록(원인 분석과 수정은 9절)

### F-01 첫 재생에서 YouTube 플레이어가 재생을 시작하지 못함(간헐)

- 해당 TC: TC-13, TC-22(마지막 전체 실행), TC-22, TC-43(작성 중 실행). 모두 재실행하면 통과했다.
- 증상:
  · 새로 연 페이지에서 첫 곡을 누르면 플레이어 상태가 -1(시작 안 됨), 위치가 시작 시각에 머문다.
  · 앱은 "이 곡을 재생할 수 없습니다(브라우저 재생 오류)"를 띄우고 재생 패널을 "선택한 곡 없음"으로 되돌린다.
  · 이 문구는 YouTube가 `onError` 코드 5(HTML5 플레이어 오류)를 보냈을 때 나오는 안내다. 앱은 설계(EX-11)대로 안내하고 멈췄다.
- 재현 절차:
  1. 새 브라우저 컨텍스트(LocalStorage 비움)로 `http://localhost:5173/team/hanwha`를 연다.

### 9.1 F-01 첫 재생 간헐 실패

- **내용**: 새로 연 페이지에서 첫 곡을 누르면 가끔 플레이어가 상태 -1에 머물고, 약 18초 뒤 `onError` 5("브라우저 재생 오류")가 온다.
- **재현 빈도(창 종류별)**: 1280×800, 새 브라우저 컨텍스트마다 첫 곡을 누르고 10초 안에 PLAYING이 되지 않으면 실패로 셌다. 세 방식을 10번씩 번갈아 4묶음 돌렸다.

  | 방식 | 실패 |
  | --- | --- |
  | headless Chromium | 9/40 |
  | 실제 창 Chromium(가상 디스플레이 xvfb) | 4/40 |
  | 실제 창 Google Chrome(xvfb) | 4/40 |

  headless에만 있는 문제가 아니다.
- **원인 분석**: 실패한 회차와 성공한 회차를 비교했다.
  - YouTube iframe이 보낸 이벤트는 두 쪽 모두 `onReady` → (곡 누름) → 3 → -1 → 3 → -1(약 120~190ms 뒤)까지 같다. 성공하면 다시 3 → 1(PLAYING)로 가고, 실패하면 -1에 머문 채 약 18초 뒤 `onError` 5가 온다. 그동안 앱은 `loadVideoById`를 한 번 부른 뒤로 플레이어를 건드리지 않는다.
  - 실패한 페이지의 요청 실패·4xx/5xx 응답·콘솔 오류는 없었다. 대신 영상 서버(`googlevideo.com/videoplayback`, SABR 방식) 응답 크기가 달랐다. 성공하면 첫 응답이 약 700 KB(영상 데이터)이고, 실패하면 105~110바이트짜리 응답이 약 2초마다 되풀이된다.
  - 그 응답을 UMP 형식(부분 번호, 길이, 내용)으로 나눠 보니 실패 응답에는 영상 부분이 없다. 부분 58의 내용이 성공 때는 `08 01`, 실패 때는 `08 03 10 0a`였다. 공개된 비공식 구현(googlevideo 라이브러리)의 `StreamProtectionStatus` 정의로 읽으면 상태 1(OK)과 상태 3(ATTESTATION_REQUIRED, 재시도 한도 10)이다. 즉 YouTube 영상 서버가 이 방문자에게 증명을 요구하며 영상을 보내지 않았다. 필드 뜻은 YouTube 공식 문서가 아니라 이 비공식 정의에 기댄 해석이다.
  - 방문자 단위인지 확인했다. 컨텍스트마다 쿠키 없는 새 방문자로 연 쪽은 5/60, 한 컨텍스트에서 페이지만 새로 열어 YouTube 방문자 쿠키(`VISITOR_INFO1_LIVE` 등)를 이어 쓴 쪽은 0/60(각 20번씩 번갈아 3묶음)이었다.
  - 의심했지만 원인이 아닌 것도 있다. 자동화 표시(`navigator.webdriver`)를 끄고 돌려도 7/60, 켠 쪽은 8/60이라 차이가 없었다. QUIC을 끄면 2/40, 켠 쪽은 7/40으로 줄었지만 없어지지는 않았다.
- **판단**: 앱 코드가 아니라 YouTube 쪽 판단이다. 쿠키 없는 새 방문자에게 가끔 증명을 요구하고, 이 서버의 브라우저 세션은 그 증명을 통과하지 못한다. 앱이 보내는 요청이 아니라 YouTube iframe 안에서 오가는 요청이라 앱이 고칠 수 없다.
- **자동 재시도 검토**: 같은 곡을 한 번 더 자동으로 시도하는 대책은 넣지 않았다. 멈춘 페이지에서 시험한 결과는 아래와 같고, 한 번도 살아나지 않았다. 방문자가 증명 요구를 받으면 같은 세션 안에서는 계속 막힌다. 오류 5에서 자동으로 다시 시도하면 효과 없이 기다리는 시간만 18초 더 늘어난다.

  | 시도 | 살아난 횟수 |

  | 같은 플레이어로 다시 불러오기(멈춘 직후) | 0/2 |
  | 같은 플레이어로 다시 불러오기(오류 5 뒤) | 0/5 |
  | 같은 플레이어로 다시 불러오기(8초 뒤) | 0/4 |

  | `stopVideo()` 뒤 다시 불러오기 | 0/3 |

  | 같은 컨텍스트에서 페이지 새로고침 뒤 다시 누르기 | 0/4 |
- **수정(테스트 환경)**: E2E는 테스트마다 쿠키 없는 새 방문자를 만들어 실제 사용(같은 브라우저를 계속 씀)과 다르다.
  - `e2e/global-setup.ts`가 시작할 때 한 번 재생에 성공한 방문자의 YouTube 쿠키(.youtube.com 쿠키 5개, 앱 LocalStorage 없음)를 `e2e/.auth/youtube-visitor.json`에 저장한다. 실패하면 새 방문자로 5번까지 다시 만든다.
  - `playwright.config.ts`의 `storageState`로 모든 테스트가 이 쿠키를 쓴다. 이 파일은 `.gitignore`로 올리지 않는다.
- **영향**: 앱 동작은 바뀌지 않는다. 테스트는 앱 LocalStorage를 비운 상태라는 사전 조건을 그대로 지킨다. 대신 E2E는 처음 방문자의 첫 재생을 더는 재현하지 않는다. 그 경우는 위의 반복 측정과 휴대폰 실기기 확인으로 본다. 실제 사용자 브라우저가 이 증명 요구를 받는지는 확인하지 못했다.
- **다시 실행한 테스트**: `e2e/playback.spec.ts`(12개)를 쿠키를 나눠 쓰지 않는 설정과 나눠 쓰는 설정으로 번갈아 3번씩 돌렸다. 나눠 쓰지 않으면 39개 중 4개 실패(TC-17, TC-17, TC-20, TC-22. 모두 상태 -1에서 20초 기다림 초과), 나눠 쓰면 39개 중 0개 실패였다. 전체 3번 반복은 9.10에 적었다.

### 9.2 K-01 플레이어 준비가 오지 않으면 복구할 수 없음

- **내용**: IFrame API 스크립트는 받았는데 플레이어 iframe의 `onReady`가 오지 않으면 `apiState`는 'loaded', `readyRef`는 false로 남는다. 곡을 누르면 기다리는 곡만 바뀌고 안내도 다시 만들기도 없다.
- **원인**: 스크립트 로드에는 10초 한도가 있지만, `new YT.Player` 뒤 `onReady`를 기다리는 데에는 한도가 없었다(`PlayerContext.tsx` 플레이어 effect).
- **수정**: `READY_TIMEOUT_MS`(10초) 안에 `onReady`가 오지 않으면 `apiState`를 'failed'로 바꾼다. 그러면 effect 정리가 그 플레이어를 치운다. 기다리던 곡이 있으면 정지하고 "플레이어를 불러오지 못했습니다"를 알린다. 다음에 곡을 누르면 기존 실패 경로대로 플레이어를 새로 만든다. `onReady`와 정리에서 타이머를 지운다.
- **영향**: 정상일 때 `onReady`는 약 0.7초에 와서 타이머만 지워진다. 실패 안내 문구와 다시 시도 경로는 스크립트 로드 실패(EX-10)와 같다.
- **재발 방지 테스트**: TC-61. 영상 iframe 요청을 막고 곡을 누르면 안내가 뜨고, 막은 것을 풀고 다시 누르면 414초부터 재생된다.

### 9.3 K-02 재생 직후 실제 일시정지를 무시함, 확인 필요 항목

- **내용**: 불러온 뒤 1.5초 안에 오는 PAUSED·ENDED는, 새 곡이 이미 PLAYING이 됐어도 위치가 끝 시각보다 앞이면 이전 로드의 신호로 보고 버렸다. 소리는 멈췄는데 화면은 재생 중으로 남는다.
- **확인 필요 항목**: 같은 규칙이 위치가 끝 시각보다 앞일 때만 무시했다. 그래서 뒤 챕터(2000초)에서 앞 챕터(100~200초)로 바꿀 때 이전 위치의 ENDED가 오면 새 곡을 끊는다.
- **원인**: `isLeftoverStop(t, seg, ms)`가 "새 곡을 아직 재생하지 않았다"는 조건 없이 시간만 봤다. 또 "끝 근처가 아님"을 `t < end - 1`로만 썼다.
- **수정**:
  - `isLeftoverStop(t, seg, msSinceLoad, playedSinceLoad)`로 바꿨다. 이번 불러오기에서 PLAYING을 받았으면 남은 신호로 보지 않는다. 위치가 새 곡 끝 시각 ±1초 밖이면(앞이든 뒤든) 남은 신호다.
  - PlayerContext는 `loadVideoById` 때 표시를 지우고 PLAYING 때 세운다. PLAYING을 받으면 자동 재생 확인 타이머(3초)도 지운다.
- **영향**: 처음 이 규칙을 만든 이유(앞 곡이 끝난 뒤 새 곡을 불러온 직후 0초 위치의 ENDED)는 새 곡이 아직 재생 전이라 그대로 걸러진다. 「응원가로」(seekTo)는 표시를 지우지 않는다. 그래서 이동 직후 실제 정지도 진짜로 처리된다.
- **재발 방지 테스트**: TC-62(E2E: 재생 확인 직후 플레이어를 멈추면 "재생이 멈췄습니다"와 정지 표시), TC-68(단위: 구간 뒤 2000초 신호, 재생 뒤 정지).

### 9.4 K-03 팀·설정 저장 실패를 알리지 않음

- **내용**: `saveTeamState`·`saveSettings`가 false를 돌려줘도 PrefsProvider가 버렸다. 새로고침하면 팀·볼륨·정렬이 말없이 이전 값으로 돌아간다(EX-15).
- **수정**: 곡 목록과 같은 규칙으로 팀·설정 키마다 실패를 한 번 알린다("설정을 저장하지 못했습니다. 새로고침하면 팀·볼륨·정렬이 이전 값으로 돌아갈 수 있습니다"). 다시 성공하면 표시를 푼다. 저장소를 아예 못 쓰는 경우는 곡 목록 쪽 알림 하나로 충분해 다시 알리지 않는다.
- **영향**: 저장이 성공하는 평소에는 알림이 없다.
- **재발 방지 테스트**: TC-63.

### 9.5 K-04 id에 /가 든 곡의 수정 화면이 열리지 않음

- **내용**: JSON 검사는 비어 있지 않은 문자열 id를 받아들이는데, 수정 경로에 id를 그대로 넣어 `a/b`는 `/songs/a/b/edit`가 되고 라우트와 맞지 않는다.
- **수정**: `SongListPage`에서 `encodeURIComponent(id)`로 경로를 만든다. React Router의 `useParams`는 풀어서 돌려주므로 `SongEditPage`는 그대로다.
- **영향**: 앱이 만드는 id(영문·숫자)는 바뀌지 않는다.
- **재발 방지 테스트**: TC-64.

### 9.6 K-05 이미 있는 상황 곡을 다시 골라 같은 제목으로 저장할 수 있음

- **내용**: 「이미 있음」 후보는 상황 곡 중복 판정에서 빠져 있어, 사용자가 선택하면 같은 팀에 같은 제목의 상황 곡이 하나 더 저장됐다(BR-14 위반).
- **수정**: 이미 있는 후보도 같은 제목 묶음에 넣는다. 팀에 같은 제목이 있으면 그 후보도 "같은 상황 곡 있음(저장 안 함)"이 되어 고를 수 없다. 제목을 팀에 없는 것으로 고치면 다시 고를 수 있다. 설계 4.6을 함께 고쳤다.
- **영향**: 이미 있는 상황 곡 줄에 「이미 있음」과 「같은 상황 곡 있음(저장 안 함)」이 함께 보인다. 선수 곡·팀 곡의 「이미 있음」은 그대로 골라 저장할 수 있다.
- **재발 방지 테스트**: TC-66.

### 9.7 K-06 같은 상황의 두 번째 곡이 다른 상황 칸을 차지함

- **내용**: 같은 상황의 두 번째 곡을 앞쪽 빈 칸에 넣어, 예를 들어 「볼넷 송 2」가 빈 아웃 칸에 들어가면 단축키 2가 볼넷 곡을 틀었다(FR-07, BR-36).
- **수정**: 제 칸이 찬 곡은 9번째 칸부터 줄을 더해 놓는다. 다른 상황의 빈 칸에는 넣지 않는다. 요구사항 FR-07과 설계 5.2를 함께 고쳤다.
- **영향**: 처음 데이터는 상황마다 한 곡이라 화면이 바뀌지 않는다. 같은 상황 곡을 더 등록한 경우에만 아래 줄이 생긴다.
- **재발 방지 테스트**: TC-67. 단일 영상 등록 E2E(TC-32)의 같은 제목 「풀카운트 송」 두 칸 확인도 그대로 통과한다.

### 9.8 K-07 팀 고르기 창에서 Space로 버튼을 누를 수 없음

- **내용**: 정지 단축키가 버튼 포커스 때문에 같은 곡을 다시 트는 것을 막으려고, 모든 버튼에서 Space의 keyup을 막았다. 버튼의 Space 누름은 keyup에서 일어나므로 팀 고르기 창의 버튼도 Space로 눌리지 않았다.
- **수정**: keydown에서 정지 단축키로 쓴 Space만 기억하고, 그 keyup만 막는다. 대화상자 안의 Space는 단축키가 아니라 기억하지 않는다.
- **영향**: 버튼 클릭 뒤 Space로 정지해도 같은 곡이 다시 시작되지 않는 것(TC-51)은 그대로 통과한다.
- **재발 방지 테스트**: TC-65.
